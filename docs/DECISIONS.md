# Decisions log

One line per ambiguous choice: what we picked and why. Newest at the bottom.

- **Standalone repository:** LOCKSTEP was first built as a subfolder of a larger repository (next to an unrelated cricket-analytics project) and was then migrated here with a **fresh, independent history**. Only the final, verified source was carried over (commit `ee2b0e9` of the original branch), as the repository root. Generated evidence (screenshots, full-size sample renders) was deliberately left behind. Entries below that mention old paths, the old branch or the sample-render mishap describe that earlier development history.
- **TypeScript 6.0.3, not 7.x:** typescript-eslint supports `<6.1`, and TS 7 is the new native compiler, which lint tooling doesn't support yet.
- **React Router 7.18 (not 8.x):** v7 is the long-term-stable line with the library-mode API we use; v8 adds nothing we need.
- **@playwright/test 1.63.0:** this matches the Chromium build that is pre-installed in the environment (so no browser download).
- **Model choice:** if `GEMINI_MODEL` is empty, the server lists the models the key can use and picks the newest *stable* `gemini-X.Y-flash`. If listing fails, it uses Google's `gemini-flash-latest` alias.
- **DST rules:** a local time that falls in a DST gap moves forward by the gap (02:30 → 03:30). An ambiguous time in a DST overlap uses the earlier instant. This is the same as Temporal's `compatible` option. The UI shows a note when either happens.
- **Midnight deadline:** a deadline at exactly 00:00 local counts as due at the end of the previous day, for day counting and the due-today state.
- **"After today" milestone rule:** milestone dates must be strictly after today, except when the deadline itself is today (then today is the only valid date).
- **Capacity:** working days from today to the deadline day, both inclusive, × hours/day. Today counts because you can start right away.
- **Capacity vs. hard errors:** date, order and working-day violations are *hard* errors that trigger the single repair call. Going over capacity is a *feasibility signal*: the plan is still shown, the code's feasibility becomes "Unrealistic" with the numbers, and the one-tap fixes appear. A plan that doesn't fit is still useful information, and refusing to show it would hide why.
- **Code feasibility thresholds:** ≤85% of capacity = Achievable, ≤100% = Tight, >100% = Unrealistic.
- **Pace:** "ahead" or "behind" when task % and time % differ by more than 5 percentage points; otherwise "on track".
- **Bottom sheet:** dropped Vaul and wrote a small non-modal sheet (`src/components/ui/bottom-sheet.tsx`). Vaul 1.1.2 always mounts Radix Dialog in *modal* mode, which hides the rest of the Studio (the header, the Export button, the nav) from screen readers with `aria-hidden`. An always-open studio sheet must not do that. Library failed once on accessibility, so we used the simpler option.
- **Sample renders:** full-size sample wallpaper renders (~2–5 MB each; film grain makes PNGs incompressible) are never committed. `npx tsx scripts/render-samples.ts` regenerates them into the git-ignored `docs/evidence/wallpapers/`. (In the original development repository they were once committed by mistake, which is part of why this repository starts with a clean history.)
- **No GSAP:** the hero's motion is a slow Three.js rotation plus a little Framer Motion. GSAP would add a library with no job to do, which the brief rules out.
- **3D hero gating:** the 3D ring loads only on ≥768px screens with WebGL2, without reduced motion or Save-Data, after the browser is idle. It's excluded from the offline precache. Everyone else sees the static SVG ring.
- **Performance budget:** to reach mobile Lighthouse 90+, the landing paints its headline without waiting for JS animation (no opacity fade on LCP text). The phone mock draws after idle. The app shell and reminders are lazy. The two hero fonts are preloaded. Icons and vendors are grouped into a few cacheable chunks. Measured: landing 93–97, /new 95–98, /guide 96. The empty dashboard on a cold profile scores 84–86, because its first headline waits for IndexedDB; recorded honestly rather than gamed.
- **AI backgrounds:** offered only when the key's model list includes an image-capable Gemini model (`gemini-X.Y-(flash|pro)-image[-preview]`; set `GEMINI_IMAGE_MODEL` to override). If a call fails with that model, the feature hides itself for an hour. The prompt forbids text, people and faces. Images are saved as local blobs, like uploads.
- **Model listing shared:** the text-model and image-model resolvers share one cached `models.list()` call, so `/api/health` lists models at most once per hour.
- **Living Wallpaper secrets:** the server stores only SHA-256 hashes of the token and secret. A wrong secret returns 404, not 403, so links can't be probed. Revoking deletes the record.
- **Status colours in light mode:** darkened (`#2f6b3d`, `#7a4f00`, `#963d32`) so badge text passes AA on its own tinted background. axe-core caught the original values.
- **Independent review (15 findings, all fixed):** (1) Living Wallpaper routes now have their own rate limits, a 64 KB body cap, hex-only colours, phone-sized custom dimensions and a per-day PNG cache. (2) Client IPs no longer trust a forgeable `X-Forwarded-For`: Vercel uses its own headers, elsewhere `TRUST_PROXY` hops (default 0). (3) Once a plan is under way, feasibility judges the *remaining* work and fixes are recomputed. (4) Ticking a task never re-opens a milestone you completed by hand. (5) "Today's focus" counts today's done work, so you can finish it. (6) Deleting a goal revokes its Living Wallpaper links. (7) Task delete/undo restores logged minutes and re-syncs completion. (8) Adding or deleting milestones re-checks goal completion. (9) The wizard blocks deadlines with no plannable working day. (10) Deadlines are capped at 3 years. (11) Reminders use the local date. (12) The coach sends at most 20 milestones. (13) Living links count days from the same start as the app. (14) Export re-renders after a refresh. (15) Studio preview uses the real device aspect, and autosave can't write one goal's design onto another.
- **Known edge left as is:** a 00:00 deadline on a day whose midnight falls in a DST gap (e.g. America/Santiago in September) counts one day late. That's rare, and the "midnight belongs to the previous day" rule is still the right default.
- **Design-critique pass:** applied the small, low-risk visual fixes (toasts, stat chips, review bar, Focus bar, Studio inspector width, export sheet, cover/landing widget slabs). Left the broader consistency work (type scale, shared content width, mobile hero, Coach card, Insights palette) for later: those touch many screens, and the Insights colours were validated for colour-blind separation, so changing them needs a re-validation.
- **Gemini schema kept to plain types:** `fullScopeHours` is a plain number (0 = full goal fits) instead of a nullable union, because I couldn't confirm union-type support (the docs host is unreachable from this sandbox) and a rejected schema would break planning outright.
- **Bug: plan generation timed out at 30 s on a real key** (reported after the first real Gemini run, model `gemini-3.8-flash`). `gemini-3.8-flash` is a real, generally available model, and a wrong model name fails instantly with a 404, so the name was not the cause. What the code showed: plan requests sent `thinkingConfig: { includeThoughts: true }` and **never set a thinking level**, so a Gemini 3.x model used its default (long, silent) thinking; the failure is a stall with no first chunk, which fits that. This could not be reproduced here (no key), so the fix was built to be verifiable on the owner's machine: (1) plan requests now ask for an explicit LOW thinking level (`thinkingLevel` on 3.x, a token budget on 2.5, unchanged for aliases; `GEMINI_THINKING_LEVEL` overrides it); (2) if Google rejects those settings with a 400 that mentions thinking, the request is retried once with plainer settings instead of failing; (3) the timeout now says *which* wait stalled (no HTTP response = network; HTTP response but no data = model thinking); (4) an `ai_diag` log line records the phase timings, the HTTP status and Google's own error text with secrets redacted (before, a 400 showed only "Gemini status 400" and the reason was thrown away); (5) `npm run diagnose:gemini` makes real minimal calls and then the full flow, and names the cause. The timeout was deliberately **not** raised.
- **Model fallback for 503 "high demand"** (the owner's real-key diagnostic showed every generation request returning 503 UNAVAILABLE for `gemini-3.8-flash`, on both `v1` and `v1beta`, with and without thinking settings: Google-side capacity, not our code). `gemini-3.8-flash` stays the primary. On a *temporary* failure (503/500/502/504/429, or no HTTP answer / no first chunk) the plan request retries the primary once and then tries at most two alternatives: **at most 4 upstream calls per plan**, because 503s count against rate limits and hammering a struggling API makes it worse. Alternatives are chosen from the key's own live model list, so a model Google retires drops out by itself (research found Google's pages disagree about `gemini-2.5-*`: a 16 Oct 2026 shutdown date, and forum reports of 404s from July 2026). **Default order (updated 2026-11-23 from the owner's real diagnostics while the primary returned 503): `gemini-3.6-flash` (OK in ~5 s), then `gemini-3.5-flash` (OK in ~23 s).** `gemini-3.7-flash` (503 / timeout) and `gemini-2.5-flash` (404, unavailable to new users) are excluded from the automatic chain for now; they remain usable through `GEMINI_MODEL_FALLBACKS`. The two preferred names are applied only if the key lists them; a free slot is filled with the newest other stable Flash model (Flash-Lite last), never a preview, `-latest` alias, pinned revision or image model. The order is a snapshot of one key at one moment: Google's capacity changes, so re-run `npm run diagnose:gemini` and override with `GEMINI_MODEL_FALLBACKS` if it changes. `GEMINI_MODEL_FALLBACKS` overrides it (`none` disables). Permanent errors on the primary (400, 401/403, 404) are never retried elsewhere because every model would fail the same way. A *fallback* that 404s is skipped rather than masking the real overload. The model list is warmed once in the background (cached 1 h), because during an outage `models.list` can 503 too. Validation, repair and feasibility are unchanged; the repair call uses the model that wrote the plan. Scope: plan generation only; the coach, motivation line and weekly summary are not covered and degrade gracefully as before. **Not verified against real Gemini**: the tests use the real SDK against a local fake server.
- **Plan schema reduced to structure; constraints enforced by the server** (the owner's real run: `gemini-3.6-flash` and `gemini-3.5-flash` both rejected the plan request with HTTP 400 "The specified schema produces a constraint that has too many states for serving"). Gemini turns `responseJsonSchema` into a state machine; bounded arrays (`minItems`/`maxItems`, nested 12 × 8), a 90-value date `enum` inside each milestone, number ranges and `format: "date"` multiply its size. The Gemini-facing schema now keeps every field, type, `required`, `propertyOrdering` and the two 3-value enums only; the counts, minute ranges and allowed dates moved to descriptions and the prompt, and stay enforced by zod + `validatePlan` + one repair call (rejected: keeping a short date enum: it is the same kind of constraint, and the prompt already lists the dates). A unit test walks the schema and fails on any state-heavy keyword. In the same fix, a permanent error (400, 403) from a *fallback* model stops the chain and is reported as is instead of being skipped and summarised as "very busy"; only temporary errors and 404s move on to the next model.
- **Slow models and quota limits (Stage 1, after the owner's real run on `ba2deac`):** `gemini-3.8-flash` 429 (free-tier quota); `gemini-3.6-flash` stalled after 13 chunks of the plan stream; `gemini-3.5-flash` wrote a valid plan in 78 s. (1) Default fallback order is now `gemini-3.5-flash`, then `gemini-3.6-flash`. (2) A 429 whose message says the quota is used up is not retried on the same model (a per-minute/per-day limit can't recover in 1–6 s); it still falls back. 503/500 and other 429s keep their one retry. (3) The repair call rewrites the whole plan, so it gets 120 s (was the 30 s small-call limit) and the thinking level that worked for the plan (LOW), without thought summaries. (4) Because 120 s per stream × 3 models + a 120 s repair could exceed Vercel's 300 s `maxDuration`, one plan request now has a shared **270 s** limit: everything is aborted with an honest TIMEOUT at 270 s, and no new model attempt or repair is started with less than 30 s left (`planBudgetMs`, `minAttemptMs`); a unit test checks the numbers against `vercel.json`. (5) The diagnostic now applies `GEMINI_MODEL_FALLBACKS` and `GEMINI_THINKING_LEVEL` in its full-flow step too (it silently ignored them), sends the app's own thinking setting first, uses the app's 120 s stream cap, and records thinking vs text chunks, the last chunk time and the longest gap (also in the app's `ai_diag` line), so the next stall shows whether the model was still thinking or stopped mid-answer.
- **Start over on another model after a mid-answer stall (Stage 2):** a TIMEOUT whose phase is `streaming` (no new chunk within `chunkIdleTimeoutMs`, or the model's own `streamTotalTimeoutMs` used up after it started answering) now moves on to the next model, like a 503; it is never retried on the same model. Before, any timeout after output had started was final, and since `ba2deac` it also stopped the chain, so `gemini-3.5-flash` was never tried after `gemini-3.6-flash` stalled. The shared 270 s plan limit (`phase: plan-time-limit`) is explicitly not a stall, and no model is started with < 30 s left, so the worst case stays under Vercel's 300 s. 400/403 never move on. The 4-call cap is unchanged (a stalled model is one of the at most 3 models). Before the next model's request is sent, the server emits a new SSE event `reset` `{reason, from, to}`; the planning page clears its preview (milestones, feasibility). Server side, each attempt has its own parser and text, and only the successful attempt's text is validated, repaired or returned, so partial output is never used. Older cached pages ignore the unknown event and only show stale preview cards until `result` replaces them. The E2E mock now serves Gemini from a local HTTP server instead of MSW: with MSW 3 on Node 22, aborting a mocked response body (what the app does to a stalled stream) crashes the process (undici `assert(!this.aborted)`), reproduced without the app.
- **Transport: keep SDK streaming, harden how we read it.** Compared offline with the real `@google/genai` 3.6.1 against a local server (no quota used): SDK streaming delivers each event as it arrives (no buffering; within ~20 ms of raw `fetch`), surfaces in-stream error events as errors, and implements Google's continuation protocol (a long answer can be split into hops; the SDK opens a new request with the `continuationToken`, on by default). Raw REST streaming would see the same events (plus SSE comments the SDK drops) but would have to re-implement continuation and error handling. Non-streaming `generateContent` does the same work on Google's side but returns nothing until the end: a stalled request could only be detected at the total timeout, and there is no progress. Rejected: raw REST, non-streaming, and a two-stage plan (skeleton, then tasks): it doubles requests per plan on a quota of ~20/day, the total output tokens stay about the same, and generating tasks without the whole plan in view risks hours and dates that don't add up (more repairs). Changed instead: (1) an answer is used only if it ends with `finishReason: STOP`; a cut-off stream (the SDK ends one without an error) or `MAX_TOKENS` is reported as an incomplete answer, never validated or repaired, and the next model starts from scratch (`reset` reason `incomplete`); (2) the app's `ai_diag` line records `finishReason`, continuation `hops` and prompt/output/thinking tokens; (3) the diagnostic observes the wire through the SDK's `fetch` hook (requests per plan, bytes, SSE comment lines, last byte) and reports CUT OFF, CONTINUATION, KEEP-ALIVES and SPEED. `maxOutputTokens` stays unset: an explicit value above a model's limit would be rejected with HTTP 400, the default is the model's maximum, and the stream caps bound time anyway.
- **Default primary model `gemini-3.1-flash-lite` (for the submission).** The owner's real run: it wrote a valid plan and the full `/api/plan` flow passed in 7.3 s with 7/7 code checks, while `gemini-3.8-flash`, `gemini-3.5-flash` and `gemini-3.6-flash` had used up their free-tier quotas (daily quotas reset at midnight Pacific, after the deadline). Rule (`chooseDefaultModel`): `GEMINI_MODEL` if set; else the default if the key lists it; else the newest stable Flash model it lists (the previous rule, so a key without the lite model still works); else the alias `gemini-flash-latest`. If listing fails, the verified default is used instead of the alias, which can point at a model whose quota is used up. The fallback chain, retries, time limits, prompt, schema and validation are unchanged (alternatives after the default: `gemini-3.5-flash`, then `gemini-3.6-flash`, or `GEMINI_MODEL_FALLBACKS`). The diagnostic picks its model with the same function and prints why.
- **Structured failure logging for Gemini (production debugging).** A failed plan on Vercel showed only `ai_run … "ok":false` and HTTP 200 (the event stream was already open), while Google's reason sat in a separate `ai_diag` line and its structured details (ErrorInfo reason, BadRequest field violations, QuotaFailure, RetryInfo) were dropped. Now every failed Gemini request logs one `ai_error` line (model, stage, attempt, latency, Google's HTTP status, status name, message, reason, field violations, quota ids, retry delay, and the app's code/status), and every `/api/plan` logs one `api_result` line with the real outcome. Parsed from Google's error body by `googleErrorInfo` (redacted, shortened; ErrorInfo metadata such as the project number and help links are left out; our own errors never get a fake Google status). The SSE transport keeps HTTP 200 (headers are sent before the outcome is known; deferring them would change streaming behaviour), so the error event now carries `status`, and an upstream 400 maps to 502 with an honest message instead of "try a different file". The planning error card titles it "Gemini rejected the request" and labels the details "Technical details" (not "What failed the checks").
- **Primary `gemini-3.5-flash-lite`; fallbacks `gemini-3.1-flash-lite`, then `gemini-3.5-flash`; 3.6 and 3.7 excluded.** Real check on the owner's key with the app's own prompt, schema and validator (`lockstep-model-check.mts`, 2026-11-23): `gemini-3.5-flash-lite` wrote a valid plan in 3.4 s (minimal request 1.6 s; finishReason STOP; JSON and schema valid; 7/7 checks; 4 milestones, 12 tasks; Achievable); `gemini-3.7-flash` timed out (30 s on a minimal request, 120 s on the plan). Fallbacks keep only models that have produced a valid plan: `gemini-3.1-flash-lite` (whole flow 7.3 s, 7/7; fast, so first) and `gemini-3.5-flash` (valid plans in ~55–78 s; slow, so second). `gemini-3.6-flash` (plan stream stalled after 13 chunks, 503s, never a valid plan) joins `gemini-3.7-flash` and `gemini-2.5-flash` in `EXCLUDED_FALLBACKS`; all stay usable on purpose via `GEMINI_MODEL` / `GEMINI_MODEL_FALLBACKS`. Worst case with the existing limits: ~30 s (primary never answers) + ~30 s + 120 s ≈ 180 s, inside the 270 s plan limit and the 4-call cap. Nothing else changed: prompt, schema, validation, timeouts, retries, UI.
- **Free-tier protection: per-model cooldown, no same-model retry on 503.** Preview runs showed every model returning 503 ("high demand") or 429 while the same model had just worked locally: free-tier capacity varies minute to minute, and calling a failing model again on every new plan only spends quota. `server/gemini/modelHealth.ts` remembers failures per model (per server instance): 503 / 500 / no answer / stall / cut-off → up to 30 s, doubling per consecutive failure, equal jitter, max 10 min, reset on success (never sooner than Google's `retryDelay`); quota 429 → Google's `retryDelay` (60 s if none), a daily quota → until midnight Pacific but re-checked at most hourly; 400/401/403/404 and cancellations → no cooldown. The fallback chain skips a cooling model without a request (`Skipped without a request …`), and so do the coach, motivation and insight calls. A 503 is no longer retried on the same model (`isRetryableUpstream`); 500 and non-quota 429 keep one retry. Model order, prompt, schema, validation, timeouts, UI and manual planning are unchanged; no paid service. Not done (deliberately, deadline): a UI countdown and a `Retry-After` for the browser.
- **When Gemini is unavailable: a starter plan built by rules, never labelled as AI.** When every free-tier model is overloaded or out of quota, the error card offers "Use a starter plan (no AI)" (`shared/starterPlan.ts`) next to Retry and the blank manual plan. It passes the same code checks as a Gemini plan, is saved as `manual` with `plan_meta.starterAt`, and is labelled "Starter plan made by LOCKSTEP's rules, not by Gemini" (milestones: "Starter (no AI)"). Rows keep `source: 'user'` because the database allows only `ai` / `user`. Considered and rejected: a saved example plan presented as Gemini output (it would not be this user's goal, and claiming it was Gemini's would be false).
