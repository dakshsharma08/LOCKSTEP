# Decisions log

One line per ambiguous choice: what we picked and why. Newest at the bottom.

- **Standalone repository:** LOCKSTEP was first built as a subfolder of a larger repository (next to an unrelated cricket-analytics project) and was then migrated here with a **fresh, independent history**. Only the final, verified source was carried over (commit `ee2b0e9` of the original branch), as the repository root. Generated evidence (screenshots, full-size sample renders) was deliberately left behind. Entries below that mention old paths, the old branch or the sample-render mishap describe that earlier development history.
- **TypeScript 6.0.3, not 7.x:** typescript-eslint supports `<6.1`, and TS 7 is the new native compiler, which lint tooling doesn't support yet.
- **React Router 7.18 (not 8.x):** v7 is the long-term-stable line with the library-mode API we use; v8 adds nothing we need.
- **@playwright/test 1.63.0:** this matches the Chromium build that is pre-installed in the environment (so no browser download).
- **Model choice:** if `GEMINI_MODEL` is empty, the server lists the models the key can use and picks the newest *stable* `gemini-X.Y-flash`. If listing fails, it uses Google's `gemini-flash-latest` alias.
- **DST rules:** a local time that falls in a DST gap moves forward by the gap (02:30 → 03:30). An ambiguous time in a DST overlap uses the earlier instant. This is the same as Temporal's `compatible` option. The UI shows a note when either happens.
- **Midnight deadline:** a deadline at exactly 00:00 local counts as due at the end of the previous day, for day counting and the due-today state.
- **"After today" milestone rule:** milestone dates must be strictly after today, except when the deadline itself is today (then today is the only valid date).
- **Capacity:** working days from today to the deadline day, both inclusive, × hours/day. Today counts because you can start right away.
- **Capacity vs. hard errors:** date, order and working-day violations are *hard* errors that trigger the single repair call. Going over capacity is a *feasibility signal*: the plan is still shown, the code's feasibility becomes "Unrealistic" with the numbers, and the one-tap fixes appear. A plan that doesn't fit is still useful information, and refusing to show it would hide why.
- **Code feasibility thresholds:** ≤85% of capacity = Achievable, ≤100% = Tight, >100% = Unrealistic.
- **Pace:** "ahead" or "behind" when task % and time % differ by more than 5 percentage points; otherwise "on track".
- **Bottom sheet:** dropped Vaul and wrote a small non-modal sheet (`src/components/ui/bottom-sheet.tsx`). Vaul 1.1.2 always mounts Radix Dialog in *modal* mode, which hides the rest of the Studio (the header, the Export button, the nav) from screen readers with `aria-hidden`. An always-open studio sheet must not do that. Library failed once on accessibility, so we used the simpler option.
- **Sample renders:** full-size sample wallpaper renders (~2–5 MB each; film grain makes PNGs incompressible) are never committed. `npx tsx scripts/render-samples.ts` regenerates them into the git-ignored `docs/evidence/wallpapers/`. (In the original development repository they were once committed by mistake, which is part of why this repository starts with a clean history.)
- **No GSAP:** the hero's motion is a slow Three.js rotation plus a little Framer Motion. GSAP would add a library with no job to do, which the brief rules out.
- **3D hero gating:** the 3D ring loads only on ≥768px screens with WebGL2, without reduced motion or Save-Data, after the browser is idle. It's excluded from the offline precache. Everyone else sees the static SVG ring.
- **Performance budget:** to reach mobile Lighthouse 90+, the landing paints its headline without waiting for JS animation (no opacity fade on LCP text). The phone mock draws after idle. The app shell and reminders are lazy. The two hero fonts are preloaded. Icons and vendors are grouped into a few cacheable chunks. Measured: landing 93–97, /new 95–98, /guide 96. The empty dashboard on a cold profile scores 84–86, because its first headline waits for IndexedDB; recorded honestly rather than gamed.
- **AI backgrounds:** offered only when the key's model list includes an image-capable Gemini model (`gemini-X.Y-(flash|pro)-image[-preview]`; set `GEMINI_IMAGE_MODEL` to override). If a call fails with that model, the feature hides itself for an hour. The prompt forbids text, people and faces. Images are saved as local blobs, like uploads.
- **Model listing shared:** the text-model and image-model resolvers share one cached `models.list()` call, so `/api/health` lists models at most once per hour.
- **Living Wallpaper secrets:** the server stores only SHA-256 hashes of the token and secret. A wrong secret returns 404, not 403, so links can't be probed. Revoking deletes the record.
- **Status colours in light mode:** darkened (`#2f6b3d`, `#7a4f00`, `#963d32`) so badge text passes AA on its own tinted background. axe-core caught the original values.
- **Independent review (15 findings, all fixed):** (1) Living Wallpaper routes now have their own rate limits, a 64 KB body cap, hex-only colours, phone-sized custom dimensions and a per-day PNG cache. (2) Client IPs no longer trust a forgeable `X-Forwarded-For`: Vercel uses its own headers, elsewhere `TRUST_PROXY` hops (default 0). (3) Once a plan is under way, feasibility judges the *remaining* work and fixes are recomputed. (4) Ticking a task never re-opens a milestone you completed by hand. (5) "Today's focus" counts today's done work, so you can finish it. (6) Deleting a goal revokes its Living Wallpaper links. (7) Task delete/undo restores logged minutes and re-syncs completion. (8) Adding or deleting milestones re-checks goal completion. (9) The wizard blocks deadlines with no plannable working day. (10) Deadlines are capped at 3 years. (11) Reminders use the local date. (12) The coach sends at most 20 milestones. (13) Living links count days from the same start as the app. (14) Export re-renders after a refresh. (15) Studio preview uses the real device aspect, and autosave can't write one goal's design onto another.
- **Known edge left as is:** a 00:00 deadline on a day whose midnight falls in a DST gap (e.g. America/Santiago in September) counts one day late. That's rare, and the "midnight belongs to the previous day" rule is still the right default.
- **Design-critique pass:** applied the small, low-risk visual fixes (toasts, stat chips, review bar, Focus bar, Studio inspector width, export sheet, cover/landing widget slabs). Left the broader consistency work (type scale, shared content width, mobile hero, Coach card, Insights palette) for later: those touch many screens, and the Insights colours were validated for colour-blind separation, so changing them needs a re-validation.
- **Gemini schema kept to plain types:** `fullScopeHours` is a plain number (0 = full goal fits) instead of a nullable union, because I couldn't confirm union-type support (the docs host is unreachable from this sandbox) and a rejected schema would break planning outright.
- **Bug: plan generation timed out at 30 s on a real key** (reported after the first real Gemini run, model `gemini-3.8-flash`). `gemini-3.8-flash` is a real, generally available model, and a wrong model name fails instantly with a 404, so the name was not the cause. What the code showed: plan requests sent `thinkingConfig: { includeThoughts: true }` and **never set a thinking level**, so a Gemini 3.x model used its default (long, silent) thinking; the failure is a stall with no first chunk, which fits that. This could not be reproduced here (no key), so the fix was built to be verifiable on the owner's machine: (1) plan requests now ask for an explicit LOW thinking level (`thinkingLevel` on 3.x, a token budget on 2.5, unchanged for aliases; `GEMINI_THINKING_LEVEL` overrides it); (2) if Google rejects those settings with a 400 that mentions thinking, the request is retried once with plainer settings instead of failing; (3) the timeout now says *which* wait stalled (no HTTP response = network; HTTP response but no data = model thinking); (4) an `ai_diag` log line records the phase timings, the HTTP status and Google's own error text with secrets redacted (before, a 400 showed only "Gemini status 400" and the reason was thrown away); (5) `npm run diagnose:gemini` makes real minimal calls and then the full flow, and names the cause. The timeout was deliberately **not** raised.
- **Model fallback for 503 "high demand"** (the owner's real-key diagnostic showed every generation request returning 503 UNAVAILABLE for `gemini-3.8-flash`, on both `v1` and `v1beta`, with and without thinking settings: Google-side capacity, not our code). `gemini-3.8-flash` stays the primary. On a *temporary* failure (503/500/502/504/429, or no HTTP answer / no first chunk) the plan request retries the primary once and then tries at most two alternatives: **at most 4 upstream calls per plan**, because 503s count against rate limits and hammering a struggling API makes it worse. Alternatives are chosen from the key's own live model list, so a model Google retires drops out by itself (research found Google's pages disagree about `gemini-2.5-*`: a 16 Oct 2026 shutdown date, and forum reports of 404s from July 2026). **Default order (updated 2026-11-23 from the owner's real diagnostics while the primary returned 503): `gemini-3.6-flash` (OK in ~5 s), then `gemini-3.5-flash` (OK in ~23 s).** `gemini-3.7-flash` (503 / timeout) and `gemini-2.5-flash` (404, unavailable to new users) are excluded from the automatic chain for now; they remain usable through `GEMINI_MODEL_FALLBACKS`. The two preferred names are applied only if the key lists them; a free slot is filled with the newest other stable Flash model (Flash-Lite last), never a preview, `-latest` alias, pinned revision or image model. The order is a snapshot of one key at one moment: Google's capacity changes, so re-run `npm run diagnose:gemini` and override with `GEMINI_MODEL_FALLBACKS` if it changes. `GEMINI_MODEL_FALLBACKS` overrides it (`none` disables). Permanent errors on the primary (400, 401/403, 404) are never retried elsewhere because every model would fail the same way. A *fallback* that 404s is skipped rather than masking the real overload. The model list is warmed once in the background (cached 1 h), because during an outage `models.list` can 503 too. Validation, repair and feasibility are unchanged; the repair call uses the model that wrote the plan. Scope: plan generation only; the coach, motivation line and weekly summary are not covered and degrade gracefully as before. **Not verified against real Gemini**: the tests use the real SDK against a local fake server.
